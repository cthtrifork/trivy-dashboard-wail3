# CI design notes

Where the GitHub Actions workflows in `.github/workflows` come from, and what was deliberately left out.

Sources:
- Wails, [Crossplatform build with GitHub Actions](https://wails.io/docs/guides/crossplatform-build/) (a Wails **v2** guide).
- [`dAppServer/wails-build-action`](https://github.com/dAppServer/wails-build-action/blob/main/action.yml), the action that guide points to (also v2: it drives the `wails build` CLI).
- Wails v3's own `build-and-test-v3.yml`, for the test job. The two sources above contain **no test step at all**.

## What was taken from them

| Practice | Source | Where here |
|---|---|---|
| Build when a tag is pushed and keep the result as an Actions artifact | guide's example workflow | `release.yml` (semantic-version tags only, artifact `release-files`) |
| `setup-go` with `check-latest: true` and a cache keyed on `go.sum`; the Go version is read from `.tool-versions` | action's *Setup GoLang* step | every workflow that installs Go |
| Print `go version` so a run records its toolchain | action's `go version` step | CI, release, security (CI and release also print the GTK/WebKit versions) |
| Detect the distribution and **fail the run if it is unsupported** rather than build anyway | action's *Linux Discovery* step | `release.yml` *Check the build distribution*: the README promises a binary built on Ubuntu 24.04, which fixes the glibc and WebKitGTK baseline |
| Set the executable bit explicitly | action's *Add Linux perms* step | CI and release build steps |
| One named artifact per platform | action's `upload-artifact` step | CI uploads `trivy-scanner-linux-amd64` (unsigned, 7 days) so reviewers can try a PR build |
| Inject a version into the binary from the tag | guide's list of enhancements | `-X …/internal/app.version=…` in release (and `ci-<sha>` in CI) |
| Cache dependencies | guide's list of enhancements | `setup-go` cache |
| Create the release when a tag is pushed | action's release step | `release.yml` attaches the build to the draft that Release Drafter writes for the tag, then publishes it through the REST API (see [releasing](releasing.md#release-notes)) |
| Test job: GTK4 + WebKitGTK 6 build dependencies, `GOTOOLCHAIN: local`, cancel superseded PR runs | Wails v3 `build-and-test-v3.yml` | `ci.yml` |
| Job graph: `lint` (gofmt, tidy, bindings; no GTK) → `vet` → `test` and `build` in parallel, so cheap failures surface before the slow race tests | this repo | `ci.yml` |

## What was left out, and why

- **Per-distro WebKit package and build tag** (the action picks `libwebkit2gtk-4.0` or `4.1` plus `-tags webkit2_41` by Ubuntu release). That is a Wails v2 / GTK3 concern. This app targets Wails v3's default GTK4 + WebKitGTK 6 backend only. A GTK3 build would be a separate asset and has not been asked for.
- **arm64 cross-compilation** (`gcc-aarch64-linux-gnu`), **Windows and macOS** matrix entries, **code signing and notarisation**: only a Linux amd64 binary is published. Provenance is covered by a build attestation and SHA-256 checksums instead.
- **The `wails build` CLI, obfuscation, Deno/Node build steps, `NODE_OPTIONS`**: the app is built with `go build`. The frontend is built first with `make frontend` (`npm ci && npm run build`, Vite, see decision 14), with the Node version from `.tool-versions` (`actions/setup-node`); the Go side only embeds `frontend/dist`. A separate step regenerates `frontend/bindings` with the `wails3` CLI at the go.mod version and fails on any diff.

## Lint and format checks

`ci.yml` also runs, in the `test` job: `make lint-frontend` (Biome lint and format check, config in `frontend/biome.json`, plus knip for unused exports and dependencies, config in `frontend/knip.json`) and `make lint-go` (golangci-lint with the config in `.golangci.yml`: default linters; staticcheck's tagged-switch quick fixes and unchecked `Close`/test-helper writes are excluded). In CI, golangci-lint runs through its own `golangci/golangci-lint-action` (SHA-pinned like the others; a prebuilt binary plus the action's analysis cache) with `args` that mirror `make lint-go`; locally `make lint-go` runs through `go run <module>@<version>`. The golangci-lint version is written twice, as `GOLANGCI_LINT_VERSION` in the `Makefile` and as the action's `version:` (Renovate reads that one itself, and the `Makefile` comment gives the pin the same depName and datasource), so Renovate bumps them in one PR, and its "golangci-lint" group puts the action's own SHA in that PR too. The Go and Node versions in `.tool-versions` are not decisions to hold back: they should follow the latest stable release, so Renovate's PRs for them ("go toolchain", "node") are merged as soon as CI is green. The wails3 CLI (about 40 s to compile, needed by `lint`, `build` and `bindings.yml`) is cached as a built binary with `actions/cache`, keyed on the Wails version in `go.mod` and the Go version; the release job still builds it from source, so a cached executable cannot reach a signed release. `make tools` installs `golangci-lint` and `goimports` into `GOBIN` for editors. `make lint` runs both locally; `make fmt` and `make format-frontend` fix formatting. The `lint` job also runs yamllint (`yamllint --strict` over `git ls-files '*.yml' '*.yaml'`, inline in the workflow, not a Makefile target) (config in `.yamllint.yml`, installed from PyPI at a Renovate-bumped version) on every tracked YAML file.

## Dependency updates (Renovate)

Self-hosted Renovate (`renovate.yml`, the `renovatebot/github-action`) replaces Dependabot, with the config in `.github/renovate.json5`.

- **What it updates:** Go modules, the frontend npm packages, Docker base images (every `FROM` line, in `build/docker/headless.Dockerfile` and `.devcontainer/Dockerfile`), the default Trivy image in `internal/trivy/engine.go` (the same `renovate:` comment, written `//` above the `const`; tag and digest move together and a digest-only change is not automerged), the SHA-pinned Actions (`helpers:pinGitHubActionDigests` keeps the `# vX.Y.Z` comment), the Go and Node versions in `.tool-versions` (Renovate's asdf manager; `go.mod`'s `go` line and the golang and node images of the Dockerfiles repeat them, so each family is one Renovate group: "go toolchain", "node", and "wails" for the Wails Go module with `@wailsio/runtime`, which must be the same version), and anything marked with a `# renovate: datasource=<ds> depName=<name>` comment on the line above its version: the Go dev tools in the `Makefile`, zizmor and the `gh-pin-actions` extension in `actions-lint.yml`, and the `podman-remote` release (`ARG PODMAN_VERSION`) in `headless.Dockerfile`. Apart from that ARG, the container files need no such comment; apt and apk packages are left to the distribution.
- **When:** weekdays (cron) and on demand, on the default branch only, so a schedule only starts once the workflow is on `main`. It also keeps the "Dependency Dashboard" issue up to date.
- **Cooldown and automerge:** a release must be 2 days old before Renovate creates a branch for it (`minimumReleaseAge` with `internalChecksFilter: strict`). Patch and digest updates then automerge; minor and major updates wait for review. Minors are grouped per ecosystem (`actions`, `go-minor`, `frontend-minor`, `dev tools`) but patches never join a group, because a group merges as a whole. The Go version (workflows, `go.mod`, Dockerfiles) is one `go toolchain` PR that is never automerged. `@wailsio/runtime` and the runner image (`ubuntu-24.04`) are not updated.
- **Security:** advisories come from OSV.dev (`osvVulnerabilityAlerts`) and, in the real run, GitHub's own alerts (through the App's Dependabot alerts permission).
- **Config lint:** the `renovate config` job in `actions-lint.yml` runs `renovate-config-validator --strict` on `renovate.json5` (version pinned with a `# renovate:` comment).
- **Dry run:** a pull request that changes `renovate.json5` or `renovate.yml` runs Renovate with `RENOVATE_DRY_RUN=full` on its own branch. It writes nothing; the job summary lists the branches and updates it would create and the step log has the full debug output.
- **GitHub App:** the real run authenticates as a GitHub App ([renovatebot/github-action, "Example with GitHub App"](https://github.com/renovatebot/github-action#example-with-github-app)) through `actions/create-github-app-token`, not with `GITHUB_TOKEN`: PRs opened with `GITHUB_TOKEN` do not start CI, so an automerge would have no checks to wait for, and the workflow's own token stays read-only. Setup: create a GitHub App with repository permissions Contents, Pull requests, Issues, Workflows and Commit statuses (read and write; Renovate posts a `renovate/stability-days` status for `minimumReleaseAge`) and Checks and Dependabot alerts (read), install it on this repository, download its private key, then add the repository variable `RENOVATE_APP_CLIENT_ID` and the secret `RENOVATE_APP_PRIVATE_KEY`. Commits go through the API as the App (`platformCommit`), so they are verified. Require the CI checks in branch protection before relying on automerge. The dry run on pull requests mints a read-only token from the same App, so it also checks the App's credentials and installation (for pull requests from branches of this repository; forks get no secrets).

## Keeping pull requests up to date

`update-branches.yml` runs on every push to `main` (and by hand). A personal account has no merge queue, so it does what the "Update branch" button does for every open, non-draft, same-repository PR by the repository owner (`--author`, the personal account) that is behind `main`: it calls the `update-branch` API (merge, with `expected_head_sha` so a branch that moved meanwhile is left alone). The merge commit starts CI again, so the PR stays mergeable under "Require branches to be up to date before merging" (add that to the branch rules, together with auto-merge on the PR, for the full effect). It uses the Renovate GitHub App's token (Contents and Pull requests write), because a push with `GITHUB_TOKEN` starts no workflows.

- **Skipped on purpose:** PRs by anyone else, `renovate/*` (Renovate rebases its own branches, and a commit it did not make makes it stop updating the branch) and `bot/*` (force-pushed by `screenshots.yml`), fork PRs and drafts.
- **Conflicts:** the update fails for a PR whose branch conflicts with `main`; the job summary lists it and the author resolves it by hand.
- **Cost:** every push to `main` re-runs CI on each behind PR.

## PR titles and release notes

Release notes and the next version come from [`release-drafter`](https://github.com/release-drafter/release-drafter) and one config, `.github/release-drafter.yml`. Three workflows use it:

- `pr-title.yml` checks that a PR title follows `type(scope)!: summary` with [`amannn/action-semantic-pull-request`](https://github.com/amannn/action-semantic-pull-request), and labels the PR with Release Drafter's autolabeler (the `autolabeler` rules of that config; the notes and version read the title, so the label is a convenience and an override). It runs on every push to the PR, because a required check belongs to the head commit and `update-branches.yml` pushes merge commits. It runs for fork PRs as a read-only title check (labelling needs write access) and skips `bot/*` branches.
- `release-drafter.yml` keeps a draft release current on every push to `main` (a preview; it publishes nothing).
- `release.yml` has Release Drafter write the notes for the exact tag, uploads the build to that draft and publishes it. `tag-release.yml` uses it to pick the version for bump `auto`.

All actions are SHA-pinned like the rest and use the workflow's own token. Details and the type table: [releasing](releasing.md#release-notes).

## Actions lint

`actions-lint.yml` runs on changes under `.github/`, on `main` and weekly: zizmor (pedantic persona, installed from PyPI at the version pinned in the workflow) audits workflows and composite actions, and `gh pin-actions workflows --latest` re-pins every `uses:` in the workflows a PR adds or changes (that job runs on pull requests only: on `main` an action can have a release Renovate has not bumped yet). The check fails on an unpinned action or one with a newer release. The tool pins immutable releases to the tag instead of the SHA; that is the same version, so it is not a failure.

## Lighthouse

`lighthouse.yml` audits the UI and fails when a score drops. (`scripts/lighthouse.sh`, `scripts/lighthouse.mjs`) builds the headless server app on recorded data (like the screenshots: no GTK, podman or network), runs Lighthouse for mobile and desktop three times each and takes the median, because a single run varies by a few points.

- **Thresholds** (minimum median score): performance 90, accessibility 95, best practices 90, SEO 90, set in `scripts/lighthouse.mjs`. They sit below the measured values (95-100) so noise does not fail a PR, but a lost compression header or an eagerly loaded editor does.
- **Where the result shows:** one sticky PR comment (`marocchino/sticky-pull-request-comment` with header `lighthouse-score`, updated on every push) and the job summary: a table of the four scores with the 🟢/🟠/🔴 bands Lighthouse uses (90 / 50), and a collapsed metrics table (FCP, LCP, TBT, CLS, Speed Index). The full HTML and JSON reports of the median run are the `lighthouse-reports` artifact (14 days). Fork PRs have a read-only token, so they get the job summary only. Pushes to `main` run the same audit with a job summary only.
- **No third-party action:** Lighthouse runs through `npx lighthouse@<version>`, with the version pinned in `lighthouse.yml` (`LIGHTHOUSE_VERSION`, kept current by the `# renovate:` comment). The browser is the runner's Google Chrome (`CHROME_PATH`).
- **Not a required check:** it has a paths filter, like the screenshots workflow.
- **What it does not cover:** only the landing page (no scan loaded). The audited build uses the dev-tag server build for the fixtures, which has the same frontend and asset middleware as the headless release but is not `-tags production`.

## Screenshots

Screenshots are never committed to `main`. `docs/screenshots/` is gitignored; `screenshots.yml` renders them in CI from the recorded fixtures (and `make screenshots` renders them locally). Committed PNGs conflicted with each other (git cannot merge binary files) and made a stream of bot PRs.

- **Pull request** (changes `frontend/**`, the fixtures or the screenshot scripts): runs `make screenshots`, uploads each image as its own unzipped artifact (`actions/upload-artifact` with `archive: false`, which takes one file and names the artifact after it) and embeds them in one sticky PR comment as a heading plus the bare `artifact-url` per image (the layout of homeserver-bootc's screenshot action; no `<img>` or `<details>` wrapper) (`marocchino/sticky-pull-request-comment` with header `screenshots-preview`) that is updated on every push. Nothing is pushed to the repository. Viewers must be logged in and the images expire with the artifacts (14 days). Fork PRs have a read-only token, so they get the artifacts on the run page and no comment. The dependency graph (06-09) is skipped here (`SCREENSHOT_VIEWS=core`): it is a canvas whose anti-aliasing varies between runs.
- **Adding or removing a screenshot** in `scripts/screenshots.mjs` needs a matching `Upload <name>` step (id `shot-<name>`) in `screenshots.yml`, because an action cannot be looped. The comment step fails with a message when the counts differ (the graph images are not counted).
- **Push to `main`** (same paths): renders everything, including the graph, and force-pushes the images as one commit on top of `main` to `bot/update-screenshots`, then keeps one **draft** PR, `Screenshots preview (do not merge)`, open from it. Its *Files changed* tab is where the current images are browsed. It is never merged: GitHub refuses to merge a draft, the workflow turns it back into a draft if someone marks it ready, and the `no-screenshots` job in `ci.yml` fails on any PR that adds files under `docs/screenshots` (add it to the required checks in the branch rules to make that airtight). The push is skipped when only the graph's canvas noise differs. If the PR is closed, the next run opens a new one.
- **`no-screenshots`** in `ci.yml` also catches a feature branch that force-adds the PNGs.
- Setup: Settings > Actions > General > "Allow GitHub Actions to create and approve pull requests" must be on. The bot branch and PR are pushed with the Renovate GitHub App's token (`RENOVATE_APP_CLIENT_ID` / `RENOVATE_APP_PRIVATE_KEY`, Contents and Pull requests write), because `GITHUB_TOKEN` pushes start no workflows and `ci.yml` would never report on the bot PR.
- The script is made as reproducible as it reasonably can be: it waits for the force-directed graph to rest instead of sleeping, pins the OpenVEX timestamps, disables animations, the graph's tie-breaking random numbers are seeded, and demo mode reports a zero footprint.

`bindings.yml` keeps `frontend/bindings` in step with the Go code: when a same-repository pull request changes Go code, it regenerates the bindings with the `wails3` CLI at the go.mod version and, if anything changed, pushes a `Regenerate Wails bindings` commit to the PR branch. The commit is pushed with the Renovate GitHub App's token (not `GITHUB_TOKEN`, whose pushes start no workflows), so CI runs on it; the second bindings run finds nothing to regenerate and exits. The CI bindings check stays as the backstop.

`security.yml` also runs `npm audit --omit=dev --audit-level=high` in `frontend/` (weekly, and when the frontend lockfile changes): runtime dependencies only, HIGH and above. It is deliberately not part of `ci.yml`, so a newly published advisory cannot block unrelated pull requests.

## Dependency scan on pull requests

`dependency-scan.yml` runs when `go.mod`, `go.sum`, the frontend manifest/lockfile or `build/docker/**` change. It scans the PR and its base with Trivy (`fs` for the repository files, and `image` for the headless image built from each side; HIGH and CRITICAL vulnerabilities). The image is built with the same tag on both sides so its targets match in the diff. The blocking image scan (HIGH and CRITICAL with a fix) is the `headless image` job in `containers.yml`. The Go template `.github/trivy/dependency-scan.tpl` (Trivy's `--format template`) writes one line per finding (file, tab, Markdown list item), and a short shell step in the workflow diffs the two lists and groups the result by file with `awk`, so the comment is a glanceable overview: counts, then the vulnerabilities added and removed by the PR under a heading per file (`go.mod`, `frontend/package-lock.json`, ...). It is not trimmed; it only lists the difference. Trivy has no template linter, so the `trivy template` job in `actions-lint.yml` (it runs whenever `.github/**` changes) renders the template from a recorded fixture with `trivy convert` and fails if no finding line comes out; run the same command locally after editing the template. The result is posted as a single PR comment that is updated on each push, and written to the job summary (PRs from forks have a read-only token, so only the summary is available there). It is informational and never fails the PR; the blocking check stays the Trivy job in `security.yml`.

`trivy-cache.yml` refreshes the Trivy vulnerability DB cache daily on the default branch (the trivy-action README's recommendation). `security.yml` and `dependency-scan.yml` restore it through trivy-action's built-in cache and set `TRIVY_SKIP_DB_UPDATE=true`, so they do not download the DB and avoid registry rate limits. If the cache is missing (never run, or evicted), the scans fail until the workflow runs once: trigger it with *Run workflow*.
